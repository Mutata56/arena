# Постановка ТЗ для этапа роадмапа

Ты пишешь техническое задание на учебный мини-проект. Заказчик это тренажёр arena,
исполнитель это человек, который учит Java с нуля и работает в поддержке WMS
(складская система, движок на Java). Проект пойдёт в его портфель на GitHub,
поэтому постановка должна выглядеть как настоящая задача из работы, а не как
упражнение из учебника.

Доменный флейвор обязателен: остатки и ячейки, волны отбора, маршруты по складу,
паллеты и короба, интеграционные сообщения между WMS и ERP, задания отборщику,
инвентаризация, приёмка и отгрузка. Никаких зоопарков, фигур и студентов.

## Размер

Два-четыре вечера работы. Один-три класса, шесть-десять публичных методов.
Больше не надо: непосильное ТЗ ученик бросит, и это хуже, чем лёгкое.

## Структура постановки (spec_md)

Разделы строго такие, заголовками второго уровня, в этом порядке:

1. `## Бизнес-контекст` откуда задача взялась на складе и зачем она нужна людям.
2. `## Функциональные требования` нумерованный список с ТОЧНЫМИ сигнатурами:
   имя класса, имена методов, типы параметров и возврата. По ним пишутся скрытые
   тесты, поэтому расхождения быть не может.
3. `## Ограничения` маркированный список: какие темы этапа обязаны быть использованы
   и чего делать не надо. Каждый пункт проверяемый.
4. `## Формат ввода и вывода` точные форматы строк, разделители, поведение на кривом
   входе (что за исключение и когда).
5. `## Критерии приёмки` маркированный список того, что будет проверяться, включая
   требование своих тестов.
6. `## Примеры` конкретные входы и выходы, из которых видно поведение.

В разделах «Ограничения» и «Критерии приёмки» вместе должно быть не меньше шести
пунктов списком: по ним код-ревью объясняет ученику свои замечания, и придумывать
требования сверх этого списка ревью не имеет права.

Про скрытые тесты в постановке ни слова: ученик их не видит и не должен знать
ни имени класса, ни имён кейсов.

## Что вернуть

Ответ это блоки с маркерами, и ничего кроме них. Каждый маркер стоит на своей строке
с самого начала строки. Внутри блоков ничего экранировать не надо: код пишется как код,
markdown как markdown. В JSON исходники не заворачивай, для них есть блоки.

```
===META===
{"slug": "korotkoe-imya-latinicej",
 "title": "Название проекта по-русски",
 "dir_name": "этап-NN-название-папки",
 "topics": ["темы этапа, которые проект задействует"],
 "must_use": [{"id": "switch", "why": "зачем это здесь по смыслу задачи"}]}
===SPEC===
полная постановка в markdown, разделами из списка выше
===STARTER Имя.java===
каркас с сигнатурами и заглушками
===SOLUTION Имя.java===
эталонное решение целиком
===HIDDEN ИмяHiddenTest.java===
скрытые тесты
===TESTS ИмяTest.java===
тесты, которые написал бы сам ученик
===END===
```

Блоков STARTER и SOLUTION может быть несколько, по одному на файл, и имена файлов
в них обязаны совпадать. Блок META это единственное место, где нужен JSON, и он там
короткий: ни постановки, ни кода в нём нет. Тройных кавычек вокруг блоков не ставь,
markdown-заборы внутри постановки при этом нормальны.

{{CONSTRUCTS}}

В must_use клади два-четыре признака, которые действительно нужны задаче,
и обязательно own_tests.

## Требования к коду

- Java без внешних библиотек, только JDK и JUnit 5. Дефолтный пакет,
  строки `package` нет ни в одном файле.
- В блоках HIDDEN и TESTS ровно по одному тестовому классу, имя файла совпадает
  с именем класса, имя класса кончается на Test или Tests.
  Класс скрытых тестов обязан отличаться по имени от того, что естественно
  напишет ученик.
- У каждого скрытого кейса стоит `@DisplayName` на русском: ученик увидит именно
  эту строку вместо ожидаемого значения, поэтому она должна объяснять случай.
- Скрытые тесты зовут только то, что описано в функциональных требованиях.
  Ни одного метода сверх постановки.
- Эталонное решение обязано само выполнять все ограничения из must_use: если
  требуешь switch, в эталоне должен быть switch.
- Эталон и скрытые тесты будут прогнаны реально. Красный эталон это отказ,
  постановка в банк не попадёт.
- STARTER это каркас с теми же сигнатурами и телом, которое бросает
  `UnsupportedOperationException`, чтобы всё компилировалось с первой минуты.
- TESTS это шесть-восемь проверок в духе того, что напишет ученик:
  счастливый путь, границы и хотя бы одно исключение.

## Требования к тексту

Только русский язык. Никаких длинных тире и стрелок в прозе (в коде стрелка
лямбды и нового switch это нормально). Без канцелярита и без обращения на «вы».
Тон рабочий: так пишет постановку тимлид, который уважает исполнителя.
