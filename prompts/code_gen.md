## Что нужно

Ровно одна задача строго по теме этой ноды. Решается за 15-30 минут.
Если тип ноды «проект», задача крупнее: два или три связанных класса либо метод
с настоящей логикой, и сложность 2.

Задача состоит из пяти частей, и все пять обязаны сходиться друг с другом:

1. Постановка на русском. Что за метод или класс написать, какие правила, какие
   граничные случаи. Публичный интерфейс (имена классов, методов, их параметры
   и возвращаемые типы) описан в постановке явно, иначе ученик не угадает сигнатуру.
2. Стартовые файлы: класс с готовой сигнатурой и заглушкой внутри
   (`return null`, `return 0`, комментарий «тут твой код»). Стартовый набор обязан
   компилироваться и обязан НЕ проходить видимые тесты: пустая заглушка, а не решение.
3. Видимые тесты: 2-3 простых случая, ученик их видит и по ним понимает формат.
4. Скрытые тесты: 4-6 случаев, включая граничные (пустой вход, ноль, отрицательное,
   один элемент, максимальная длина). Их ученик не видит, ему показывают только
   названия случаев.
5. Эталонное решение: те же файлы, что в стартовом наборе, но написанные целиком.
   Оно прогоняется автоматически против видимых и скрытых тестов, и если хоть один
   тест красный, задача в банк не попадёт.

## Технические требования, нарушение любого убивает задачу

- Пакетов нет. Ни одного `package`, все классы в дефолтном пакете.
- Ключи в `starter_files` и в `reference_solution` совпадают один в один, включая имена файлов.
  Имя файла это имя public-класса плюс `.java`.
- В `visible_tests` ровно один файл с ровно одним тестовым классом, имя класса
  заканчивается на `Test`. То же самое для `hidden_tests`, но имя класса другое.
- JUnit 5: `import org.junit.jupiter.api.Test;`,
  `import org.junit.jupiter.api.DisplayName;`,
  `import static org.junit.jupiter.api.Assertions.*;` (перечисли нужные явно).
- У каждого скрытого случая стоит `@DisplayName("...")` на русском: это единственное,
  что ученик увидит вместо ожидаемого значения. Пиши осмысленно: «пустой список»,
  «отрицательный остаток», а не «случай 3».
- Скрытые тесты зовут только те методы, которые описаны в постановке. Приватных
  внутренностей эталона в них нет.
- Тесты не читают файлы, не лезут в сеть, не спят и не зависят от времени,
  случайных чисел, хеш-кодов и порядка обхода HashMap. Прогон идёт без сети
  и с минутным потолком.
- Тесты не печатают в System.out и не подменяют его.
- Решение и тесты не запускают потоки и не создают процессы.

## Форма записи

```
{
  "title": "короткое название задачи, как заголовок",
  "statement_md": "постановка на русском в markdown, можно списки и блоки кода",
  "difficulty": 0,
  "starter_files": {"Warehouse.java": "public class Warehouse {\n ... \n}"},
  "visible_tests": "исходник файла WarehouseTest.java целиком",
  "hidden_tests": "исходник файла WarehouseHiddenTest.java целиком",
  "reference_solution": {"Warehouse.java": "public class Warehouse {\n ... \n}"},
  "checkstyle_hints": ["на что посмотреть в своём коде, одна строка на пункт"]
}
```

Эта запись кладётся в список `items` из общего контракта ниже, и запись там ровно одна.

`difficulty` это 0, 1 или 2: 0 это один метод в десяток строк, 1 это метод с разбором
случаев или простой класс, 2 это несколько классов или заметная логика.

Внутри значений `starter_files`, `visible_tests`, `hidden_tests` и `reference_solution`
лежит настоящий исходник на Java с переводами строк `\n`. Там можно всё, что есть
в языке, включая лямбды со стрелкой: запрет на стрелки касается человеческого текста,
а не кода. В `title`, `statement_md` и `checkstyle_hints` стрелок и длинных тире быть
не должно.

Примеры бери из обычной жизни: покупки и чеки, расписание, оценки, список дел,
температура за неделю, имена и пароли, счёт в игре. Никакой специфики предметной области:
складские ячейки, паллеты и волны отбора человеку со стороны ничего не говорят, а разбирать
он должен язык, а не чужую отрасль.
